# Enterprise AI Workflow Lab — 公开边界

本文件是未来 Public GitHub Repository 与 GitHub Pages 的发布边界。`private_sources/` 是**仅供内部核对**的事实来源，已由 `.gitignore` 排除；忽略规则不能代替逐文件审查。当前两份 Stage 0 文档可以作为拟公开文本审查，但未经发布前检查，不自动视为已获公司授权的公开材料。[依据：`private_sources/企业AI工作流调研报告.pdf` §2.4、§13；本项目用户约束]

## 1. 可以公开的内容

- 通用 AI workflow 思路：输入校验、确定性处理、模型处理、异常分支和人工复核。
- 公开化后的四层架构思想：数据接入、工程处理、模型处理、业务治理。[调研报告 §3.5]
- JSON Parse、Schema、字段类型、枚举、虚构分类路径与原文证据检查等通用工程问题。[调研报告 §4.7、§9.5、§10.2]
- OCR/ASR 错误传播、RAG 误召回、Human-in-the-loop 等**一般性风险解释**；不得暗示已验证本公司真实错误率。[调研报告 §9–10]
- 完全新编的业务文本、字段、分类规则、界面流程图、代码及浏览器本地演示结果。

## 2. 必须重新抽象或虚构的内容

- 会话、附件、质检与知识库场景：只保留可解释的机制，重新写输入、输出和案例；不直接搬运报告中的示例与截图。
- 分类树、标签、枚举、质检规则：另造最小教学规则，并在页面标明「虚构演示规则」。
- 工作流图：根据通用节点自行重画；不得描摹或裁切内部工作流截图。
- 部门工作方式、数据流及技术参数：只叙述高层通用设计；不保留可反推具体系统的名称、数值、节点标识或组合细节。
- 个人履历与答辩材料：仅保留必要的实习身份和本人真实的学习、观察、参与、梳理、拆解、分析、总结；不复制申请表或证明原件。

## 3. 明确禁止公开的内容

- 真实客户姓名、电话、身份证号、保单号、工单、完整通话和真实附件；申请表中的个人照片、学号、证件号码、联系方式及公司联系人信息也不进入仓库。
- 内部 IP、URL、API 地址、服务器路径、`user_id`、`app_id`、`workflow_id`、内部账号、权限信息、token、密钥、日志、系统配置和部署细节。
- 原始完整 Prompt、完整质检规则库、内部知识库内容、产品条款或无法确认是否允许公开的内部信息。
- 原始内部 workflow 截图、知识库配置截图，以及包含它们的报告页、成果展示页或局部裁图；已有遮挡也不足以证明可公开。
- `private_sources/` 下的任何原文件，或由原文件导出的页面图片、文本摘录包。上述文件中有身份证号、印章、联系人、内部界面及参数等内容。[材料核对：全部 S1–S5，索引见 `project_spec.md`]

## 4. 本人实习角色表述边界

可写：「在信息科技部实习期间，学习、观察并参与相关工作，梳理与拆解工作流，形成调研分析和总结。」[实习证明；实习总结；评选申请表]

不可写：「主导」「负责」「独立设计或开发公司系统」「部署」「推动上线」「向公司正式交付系统」「提升了真实业务准确率或效率」。现有材料支持调研与方法性收获，不支持这些工程贡献或运行效果结论。[调研报告 §2.4、§13.3]

## 5. 对中国融通财险及公司系统的表述边界

可在必要的履历语境中如实说明实习单位、部门和时间；涉及公司名称的最终公开措辞仍应在发布前人工确认。不得借公司名称、印章、Logo 或内部界面暗示该 Demo 获公司认证、授权、采用或属于公司系统。不可根据有限截图推断完整架构、生产状态、正式规则、运行表现或真实业务效果。[实习证明；调研报告 §1.1、§2.4、§13.3]

## 6. Workflow Guardrail 的正确表述

统一表述：「**实习结束后，基于实习调研中发现的通用问题进一步完成的公开、脱敏成果转化。**」

补充说明：「案例及分类规则完全虚构；工具在用户浏览器本地检查模拟 LLM JSON 的格式、演示 Schema、演示分类路径和有限的字面证据，并提示人工复核。它是教学 Demo，不是中国融通财险内部正式系统、保险业务规则引擎、真实 LLM 服务或自动决策工具。」

不得将 `PASS` 解释成真实保险业务可直接执行；不得把「没有找到字面证据」说成已经证明事实不存在；不得声称已经过真实业务数据验证。

## 7. Public GitHub 发布前必须再次检查

1. **仓库内容：** 检查待提交文件、Git 历史与构建产物；确认 `private_sources/` 和导出图片、PDF、临时文件、密钥均未进入公开仓库。仅有 `.gitignore` 不足以覆盖历史或被强制添加的文件。
2. **文本与代码：** 搜索姓名、电话、证件号、保单号、内部域名/IP/URL、路径、账号、ID、token、原始 Prompt、规则及配置数值；逐项人工确认所有命中。
3. **图像与元数据：** 检查页面、截图、图片元数据和提交附件；不使用原始公司界面截图、印章、Logo 或现有报告页面。
4. **案例真实性：** 确认每个示例重新虚构，分类树与规则不对应公司内部原件，并在页面可见地标注教学属性。
5. **事实措辞：** 检查 README、页面、演示词与答辩材料的时间线、本人角色、公司关系和效果宣称；必要时由本人确认公司名称可否在公开仓库出现。
6. **浏览器行为：** 检查没有网络提交输入、外部分析脚本、API Key、日志或持久化敏感文本的代码；确认 GitHub Pages 无登录即可访问。
