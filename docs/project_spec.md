# Enterprise AI Workflow Lab — Stage 0 项目规格

> 本文保留 Stage 0 的方案与材料追溯记录。最终 Demo 实际采用四项自动检查；功能与测试结果以 `audit_stage1.md` 为准。下方提到的六节点流程和额外字段检查属于早期预案。

## 1. Project Overview

**结论：保留 Workflow Guardrail 方向。** 它是实习结束后，基于实习调研中发现的通用问题进一步完成的公开、脱敏成果转化。核心演示是一款可在浏览器本地运行的「AI 结构化输出检查器」：用户输入原始文本及一段模拟 LLM JSON，点击 **Run Workflow**，逐节点看到数据为何可以或不可以继续使用。它不是中国融通财险内部正式系统，也不是实习期间开发或部署的工具。

目标交付形态为无需登录的 Public GitHub Repository 与 GitHub Pages 在线 Demo；Stage 0 只确定规格。优先服务大连理工大学盘锦校区优秀实习学生评选的 3 分钟答辩，让非技术评委在一次点击中理解「格式像 JSON」与「内容可被信任」的差别。[S1 §4.7、§9.5、§10.2；S2 第 2、5 页]

## 3. 为什么源自这次实习调研

调研中的会话总结流程将文本交给模型生成摘要、标签和分类，再做字符串格式化。材料明确指出，清除 Markdown 代码块和换行不等于 JSON 解析、类型、必填字段、枚举或三级分类路径验证；未经验证的字符串可能被误当作可直接交给下游的数据。[S1 §4.1–4.8、§9.5；S3]

调研还将企业 AI 抽象为数据接入、工程处理、模型处理、业务治理四层，并强调有依据的人工复核。Workflow Guardrail 将其中一个很小的交界点做成可操作演示：**给定一份模拟模型输出，检查其结构、约束及原文证据，并指出需要人复核的地方。** 它不复刻被观察的公司工作流。[S1 §3.5、§10.1–10.2；S2 第 2 页]

## 4. 具体问题与目标用户

**问题：** 一段可解析的 JSON 仍可能缺字段、字段类型错误、分类值不在约定范围内，或把原始文本没有的内容写成事实。若只看花括号和流畅措辞，容易高估结果可靠性。[S1 §4.7、§9.5]

**主要用户：** 3 分钟答辩现场的非技术评委。次要用户是希望学习 AI workflow 中数据契约与人工复核概念的学生。界面应先展示直观结论，再允许查看每个节点的理由；不要求用户懂保险业务或编程。

## 5. Stage 1 最小功能

1. 单页面，两个可编辑文本框：原始业务文本、模拟 LLM JSON 输出。
2. 一个 **Run Workflow** 按钮；点击后在浏览器本地顺序执行六个检查节点。无真实模型调用、上传或持久存储。
3. 页面初始填入一个**重新虚构**的失败案例；允许用户修改 JSON 后再次运行，看到节点状态变化。
4. 每个实际执行的节点显示 `PASS`、`WARNING` 或 `FAIL`，附一条简短中文解释；前置失败使后续节点无法执行时，明确标示「未运行」，不伪称检查通过或失败。
5. 结果区给出「发现的问题」及「建议人工复核／当前演示检查未发现阻断项」的结论。该结论只针对这套教学规则，不代表真实业务可自动流转。

## 6. 页面结构

- 顶部：名称、一句话问题说明、明确的公开脱敏教学 Demo 声明。
- 输入区：原文与模拟模型输出；一个运行按钮。
- 流程区：`Input → JSON Parse → Schema Check → Business Rules → Evidence Check → Human Review`，用颜色和文字共同表达状态。
- 结论区：用普通语言解释哪些字段有问题、为何不能直接采用、下一步由谁复核；不展示保险责任判断。

## 7. 内置演示案例

**原始文本（新编）：**「一位用户咨询辽宁地区某虚构保障产品需要准备哪些申请材料。」

**模拟输出（新编）：**

```json
{
  "province": "辽宁",
  "city": "上海",
  "level1": "服务咨询",
  "level2": "材料办理",
  "level3": "错误分类"
}
```

本 Demo 自行编造一条最小分类路径：`服务咨询 → 材料办理 → 材料清单`。这**不是**任何公司的真实分类树或理赔规则。预期结果：JSON Parse 与 Schema Check 通过；Business Rules 因 `level3` 不在虚构路径内而失败；Evidence Check 提示 `city = 上海` 未在原文找到直接证据；Human Review 提示需回看原文并修正，结果不能直接采用。不要将「未找到字面证据」表述为模型必然虚构；自动检查有能力边界。[问题机制：S1 §4.5、§4.7、§9.5；案例内容：本项目新编]

## 8. Workflow 节点与基本判定

| 节点 | PASS | WARNING | FAIL |
| --- | --- | --- | --- |
| Input | 两段输入均非空 | — | 任一输入为空或仅空白 |
| JSON Parse | 模拟输出可被严格解析为 JSON 对象 | — | 语法错误，或解析结果不是对象 |
| Schema Check | `province`、`city`、`level1`、`level2`、`level3` 均存在且为字符串；允许 `city` 用空字符串表示未知 | — | 必填字段缺失、类型不符或出现未约定字段 |
| Business Rules | 分类为本 Demo 虚构的合法完整路径；地区字段采用本 Demo 约定格式 | — | 分类路径不合法，或违反明确的演示规则 |
| Evidence Check | 非空地区值在原文中能找到直接字面对应 | 地区值无法找到直接字面对应，或需要语义解释 | — |
| Human Review | 前面没有 `WARNING` 或 `FAIL`，仅表示本 Demo 未发现阻断项 | 任一节点 `WARNING` 或 `FAIL`，提示人工核对原文与输出 | — |

判定顺序固定。`FAIL` 不应被后续 `PASS` 抵消；解析失败时后续依赖 JSON 的节点标示「未运行」。`Evidence Check` 只做可解释的字面核对，不承诺理解同义词、地址归属或完整事实真实性。即使全部 `PASS`，也不能声称真实业务系统可直接采用。[规则设计：本项目 Stage 1 方案；依据问题：S1 §4.7、§10.2、§13.3]

## 9. 明确不做什么

不做真实 LLM 调用、OpenAI API、OCR/ASR、RAG、正式保险规则引擎、真实客户数据处理、数据库、登录、后端、上传、生产系统集成、自动业务决定、实际准确率或效率宣称；不引入 React/Vue 或复杂 CI/CD。Stage 1 以 HTML、CSS、Vanilla JavaScript 实现本地浏览器交互，后续才考虑 GitHub Pages 发布。

## 10. Stage 1 验收标准

- 打开页面即可使用；无需账号、服务端或 API Key，刷新后不保留用户输入。
- 预置案例一次点击后明确显示：JSON 合法、分类路径失败、城市缺直接文本证据、建议人工复核。
- 把 `level3` 改成演示合法值、把 `city` 改为空字符串后重新运行，相关问题消失；改成非法 JSON 或删去必填字段时，能分别指出解析或 Schema 问题。
- 六个节点的状态与理由可读，前置失败后的节点显示「未运行」；颜色之外保留文字状态。
- 页面明确声明案例及规则虚构、仅作教学演示，所有输入只在本地处理；仓库与页面不含 `private_sources/` 原件、截图或真实内部参数。
- 非技术人员在 20–30 秒内能看懂「看似完整的 JSON 也需要验证与复核」。

## 11. 答辩现场 20–30 秒演示词

「实习中，我观察并拆解了 AI 把客服文本整理成标签和分类的工作流。我发现，输出长得像 JSON，不等于里面的内容已经可靠。这是我**实习结束后**基于这一通用问题做的公开、虚构 Demo。点击运行：JSON 语法通过了，但分类不在演示规则里，城市也找不到原文证据，所以工具建议人工复核。它展示的是 AI 输出进入下一步前，需要做哪些检查。」[实习依据：S1 §4、§9.5；工具与措辞：本项目方案]
