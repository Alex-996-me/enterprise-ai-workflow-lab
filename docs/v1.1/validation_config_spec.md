# v1.1.0 — Validation Config Spec

> 一个足够小、可由普通用户填写的检查配置。它不是 JSON Schema，也不提供规则脚本。所有配置仅在当前浏览器会话中使用。

## 1. 内部数据结构

```js
{
  requiredFields: ["product", "problem", "action"],
  evidenceFields: ["product", "problem", "action"],
  enumRules: {
    action: ["换货", "退款", "维修"]
  }
}
```

`requiredFields` 和 `evidenceFields` 是顶层字段名数组；`enumRules` 把顶层字段名映射到允许的字符串值数组。字段名按**字面键名**读取，不把点号解释为嵌套路径；读取时只检查 JSON 对象自身属性。输出中的其他未配置字段可保留，但本工具不检查它们。

## 2. 三类配置的语义

| 配置 | 当前检查 | 空配置时节点 |
| --- | --- | --- |
| `requiredFields` | 指定字段必须存在，且值为非空字符串、数字或布尔值；`0` 与 `false` 合法，`null`、空白字符串、数组和对象不合法。 | 字段契约：**未配置**。 |
| `evidenceFields` | 对指定字段的标量值做原文逐字包含检查；未找到为 **WARNING**，只称“缺少原文直接证据”。 | 原文证据：**未配置**。 |
| `enumRules` | 指定字段的字符串值必须属于相应允许值列表；不在列表中或实际值不是字符串为 **FAIL**。只做单字段比较。 | 业务规则：**未配置**。 |

`JSON.parse` 与顶层对象检查始终运行。原始材料和模拟输出均不能为空。字段契约没有隐含的保险字段、额外字段禁令或完整类型系统。

## 3. 输入与配置校验

- 三个属性必须存在且类型正确；数组和允许值中的元素均为非空字符串。界面在保存配置时去除首尾空白并去重。空数组和空 `enumRules` 合法，表示该项未配置。
- `evidenceFields` 和 `enumRules` 的字段名必须包含在 `requiredFields` 中，避免规则指向一个未检查是否存在的字段。字段名是顶层键名，可用中文；不允许空名。
- 每条枚举规则必须至少有一个允许值；比较时对实际字符串和允许值去除首尾空白，仍保持大小写及其余字符的精确比较。
- 配置本身有误时，显示 `$config` 问题并“已拦截（配置错误）”；自动检查不伪称通过，也不把配置错误解释为模型输出事实错误。
- UI 使用逗号分隔的字段列表，以及“字段名 + 用 `|` 分隔的允许值”规则行。普通用户无需编辑内部对象、JSON Schema、正则或代码。

## 4. 执行与显示顺序

1. 校验两段输入与配置结构；失败时停止，并说明错误位置。
2. JSON 解析；失败则已配置的后续节点显示“跳过”，未配置节点仍显示“未配置”。
3. 字段契约；失败时依赖这些字段的已配置规则与证据节点显示“跳过”。
4. 枚举规则和证据检查分别运行；即使枚举失败也继续呈现证据警告，最终闸门按 FAIL 优先。

通过数只统计**实际执行且通过**的节点；`跳过`和`未配置`分别计数，不计入 PASS。如果三个内容检查都未配置，只有 JSON 解析通过时闸门仍为“需要人工复核”，提示“仅检查格式，尚未配置内容检查”。若至少一个内容检查已配置且全部执行通过，可显示“可进入人工复核”，并列出未配置项。

## 5. Evidence Match 边界

字段值为字符串时去首尾空白；数字或布尔值转成相应文本（例如 `128`、`false`）再用 `sourceText.includes(valueText)` 检查。仅检查逐字包含，不做同义词、大小写折叠、OCR、语义判断或外部事实查询。数字格式、单位、改写和转述可能产生警告；警告不证明输出错误。问题路径采用 `$.action` 等可读形式；特殊键名用安全的括号表示法，不执行键名。

## 6. 三个配置实例

### 客服意图分类（预期证据警告）

```json
{
  "requiredFields": ["category", "intent", "urgency"],
  "evidenceFields": ["category", "intent", "urgency"],
  "enumRules": {
    "category": ["配送", "售后"],
    "urgency": ["一般", "紧急"]
  }
}
```

### IT 服务工单（预期全部通过）

```json
{
  "requiredFields": ["system", "issue", "severity"],
  "evidenceFields": ["system", "issue", "severity"],
  "enumRules": { "severity": ["一般", "紧急"] }
}
```

### 自由模式：蓝牙耳机（核心验收案例）

```json
{
  "requiredFields": ["product", "problem", "action"],
  "evidenceFields": ["product", "problem", "action"],
  "enumRules": { "action": ["换货", "退款", "维修"] }
}
```

原文：“客户反馈购买的蓝牙耳机左耳没有声音，希望直接换货。”输出 `{"product":"蓝牙耳机","problem":"左耳没有声音","action":"换货"}` 时，四项检查均通过。只将 `action` 改为“退款”后，枚举仍通过，证据节点对 `$.action` 给出 WARNING：“输出值‘退款’未在原始输入中找到直接依据。”闸门为“需要人工复核”。

## 7. 明确不支持

不支持嵌套字段路径、跨字段条件、完整类型声明、正则、计算表达式、脚本执行、标准 JSON Schema、语义证据匹配或自动事实核查。保险模板的枚举只约束各字段的允许值，**不能**据此声称检查了完整层级组合。
